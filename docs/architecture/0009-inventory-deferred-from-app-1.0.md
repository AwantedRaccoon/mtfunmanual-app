# ADR 0009：库存从 App 1.0 后置

- 日期：2026-07-25
- 状态：已接受
- 适用版本：App 1.0
- 关联产品范围：[MTF不全书 App 产品规划方案 1.0](../product/MTF不全书-App-产品规划方案-1.0.md)
- 部分取代：[ADR 0002：Batch 0 本地后端合同冻结](0002-batch-0-contract-freeze.md) 中所有把库存、lot ledger、库存扣减或库存测试作为 App 1.0 范围与发布门禁的条款

## 背景

原始 App 1.0 规划把可选库存、lot 分配、自动扣减、余量预测和补充提醒作为 Batch 4。实施前调查确认，当前 Schema V1–V7 和生产源码尚未建立库存模型、库存写入或库存界面；Batch 3 已经独立完成“封存方案 → 今日事项 → 中性设备本地提醒”，提醒不依赖库存。

产品负责人在 2026-07-25 决定不要求用户持续维护批次、数量、开封日和有效期。库存数据只有在持续录入时才可靠，而遗漏录入容易让余量预测失真；这与 App 1.0 的低负担目标不一致。

“多数用户不会录入库存”是本次产品判断，不冒充遥测或定量研究结论。App 1.0 不为验证该判断加入遥测。

## 决策

1. 库存、lot ledger、自动扣减、余量预测、低库存提示和补货提醒不进入 App 1.0。
2. Batch 4 编号保留，以维持既有文档、提交和阶段引用稳定；其状态改为“移出 App 1.0，需求验证后另行立项”，不重编号 Batch 5–9。
3. App 1.0 的日常提醒继续由 Batch 3 的封存方案与计划规则确定性派生。提醒偏好、一次 snooze、Countdown 提醒、权限、预算、覆盖和错误可见性继续分别遵守 ADR 0006 与 ADR 0008。
4. App 1.0 不新增 `InventoryLedgerEntry`、lot、`ConsumptionRule`、库存 reconciliation、库存迁移或库存 UI，也不把库存列入测试矩阵、发布门禁或 App Store readiness 条件。
5. 当前没有已持久化库存事实，因此本次范围调整不需要数据迁移、删除或兼容层。
6. 未来若用户研究证明库存具有足够价值，必须重新立项并建立新的产品与架构决策；届时重新评估录入负担、lot policy、单位换算、事务边界、隐私、安全性与迁移，不直接恢复旧规划为默认实现。

## 对 ADR 0002 的影响

ADR 0002 的时间、执行、化验、数据谱系、无运行时网络和发行门禁继续有效。以下库存相关内容仅保留为历史设计记录，不再约束 App 1.0：

- 执行事务与库存 consume/reversal 的联动；
- “库存事实与 lot 分配”章节；
- 库存默认 lot policy 未决门禁；
- iOS 17 实现后果与最低测试不变量中的库存条目；
- 非目标和后续批次中把库存视为待实现 1.0 能力的表述。

本 ADR 不改变 `AdministrationEvent` 的 append-only 事实、方案 occurrence、提醒、化验、附件、系统备份或本地无网络合同。

## 后果

### 正向

- 用户只需维护方案和提醒意图，不必为获得日常提醒建立库存账本。
- 避免把过期或漏记的库存估算展示为可信余量。
- 移除尚未产生用户数据的模型、迁移、事务和测试复杂度。
- Batch 6–9 与真机/发行门禁可以按真实产品价值继续推进。

### 代价

- App 1.0 不提供缺货预测、补货日期或批次/有效期管理。
- 用户需要在 App 外自行管理供应。
- 将来重新引入库存时必须重新完成需求验证和架构评审，不能假定旧 lot policy 仍适用。

## 验收

- README、产品规划和根 `AGENTS.md` 不再把库存描述为 App 1.0 待实现能力或发布门禁。
- README 保留 Batch 4 编号并明确其后置状态。
- App 1.0 的方案提醒仍归属 Batch 3，不重新包装为 Batch 4。
- Release Schema、正式 UI 和测试中不存在为了未来库存而加入的生产空壳。
